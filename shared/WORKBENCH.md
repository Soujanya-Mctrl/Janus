# Agent workspace setup

The current phase adds `/dashboard/agents` and `/dashboard/credentials` to the existing frontend. The upstream frontend was fast-forwarded before implementation; prior simulation, Docker and other workspace edits are retained. This is local repository implementation, not a separately hosted Site or a production deployment.

## Start and inspect

Install through root `npm run setup` (now includes the isolated CRE module). Start `npm run dev`; open `/dashboard/agents`. The credential-free preset Run simulation action starts real parallel worker threads, streams backend events and displays completed accounting. It uses synthetic quotes and scripted proposals. Signed-in users can edit/save roles and allowances, assign credentials/models, retrieve completed runs and resume the original run ID. Keys or accounts are not needed for the fixture.

## Credentials and live models

Existing Privy app ID and server verification PEM configure authentication through `frontend/.env.local`. All credential and configuration routes verify the bearer token. Keys are encrypted with AES-256-GCM and identity-bound additional authenticated data; only label/provider/ID/timestamp metadata is returned. Credential references are scoped to the same verified account. Revocation removes a key and causes future runs referencing it to fail rather than silently choose another credential.

Supported adapters: OpenAI Responses, Anthropic Messages, Gemini generateContent, OpenRouter Chat Completions and Groq Chat Completions. All outbound endpoints are fixed HTTPS destinations with redirects rejected; users cannot enter an arbitrary secret-exfiltrating URL. Enter a provider-specific model ID on the Agents page; availability and tool compatibility must be verified with that account. Saving a key does not call the provider. Live runs require the explicit separate-provider-billing checkbox and issue one orchestrator call followed by three worker calls. Prompts and synthetic snapshots go to the selected providers; API keys do not go into prompts or worker-thread messages. Model proposals remain subject to the paper risk engine.

`JANUS_VAULT_KEY` is an optional server-only base64 encoding of exactly 32 random bytes. Local development creates an ignored `.workbench-state/vault/master.key` when no key is configured. Back up that key and the encrypted vault together for local recovery; possession of both permits decryption. Production must inject the master key separately through its secret manager and use private persistent storage and HTTPS. OS file modes are best-effort on Windows, not a substitute for host ACLs. Do not put private keys or LLM keys in `NEXT_PUBLIC_*` variables. `NEXT_PUBLIC_ARKIV_ACCESS_KEY` is a public origin-restricted RPC access key, a different credential type.

`JANUS_WORKSPACE_ROOT` optionally identifies the monorepo checkout; `JANUS_WORKBENCH_STATE_DIR` selects private persistent storage. Defaults use the checkout and ignored `.workbench-state/`. The API spawns the fixed backend workbench script and passes selected secrets through stdin, not argv or files. Retained run metadata, model outputs and paper journals are private filesystem records but are not encrypted like the credential vault. Keep backups and never publish these directories. A full workspace checkout is required; a frontend-only standalone deployment is not supported yet.

## Recovery and scope

The web client streams actual backend events rather than synthesizing telemetry. A browser disconnect does not kill the child process; a signed-in user can retrieve its final result by run ID. Resume uses the original saved configuration and persisted inference results. The workbench journals an inference intent before submission. A missing result after submission is an uncertain billing outcome, so resume fails closed and asks for provider reconciliation rather than automatically repeating the request. Unknown outcomes can require manual reconciliation; do not delete intent files as a retry strategy. A newly created run is a new set of potentially billable requests, not recovery of an existing run. An exclusive run lock prevents concurrent resumption; killed processes can leave stale locks that require inspection.

Trading PnL, account transfers and operating fees are simulated. Real model-provider invoices are external and are not paid by paper profits. Use provider account spending limits. The paper budget does not cap the API bill. No exchange order, token approval, swap or wallet payment is submitted by a workbench run. At most two child simulations run per frontend process; this is a single-host prototype, not a distributed scheduler or production abuse-control system. Guest fixture runs are retained under an anonymous fixture namespace and contain no account secrets; operators must manage retention rather than accumulating unlimited demo runs.

## Sponsor setup after accounts are available

Hedera: the Integrations check reads chain ID and contract-code presence for the pinned testnet deployment. It submits no payment and does not verify treasury runtime identity, x402 compliance or full payment flow. Existing merchant/SDK setup remains in `MERCHANT_LIVE_SETUP.md`; complete that end-to-end separately before claiming sponsor acceptance.

Arkiv: `frontend/src/lib/arkiv-directory.ts` uses the official SDK and Rabdi schema `janus.worker.v1`. Connect a dedicated wallet, acquire test tGLM, optionally configure an origin-restricted RPC access key, and publish a one-hour public profile through a wallet signature. Read and apply the profile in the UI, then save the resulting agent configuration. Record actual writer address, entity key and transaction hash. See the `/arkiv/` documents and runnable query; no live directory evidence is claimed yet.

Chainlink: `backend/cre/` includes the official SDK, project/workflow YAML, staging config, wrapper command and a typed workflow. Install the official CRE CLI, create an account and run `cre login`. In `risk/config.staging.json`, configure nonzero Sepolia token/owner addresses. The workflow assumes six-decimal token base units for comparison with micro-USD; choose the matching test asset. Run the frontend at the configured `riskApiUrl` port or set a reachable HTTPS URL, then `npm run cre:simulate` from the repository root. It reads a token balance on Sepolia and the explicitly synthetic `/api/risk` response, applies a profit/cash/balance check and returns an advisory paper-only report. The risk endpoint is a fixed public fixture, not any user's portfolio. No signed report is consumed as financial authorization. This workflow is prepared and typechecked, but the official CLI simulation has not run without account setup; local Node tests are not CRE evidence. No deployments or cross-chain fund movement are implemented.

## Verification

Offline tests cover encryption, identity isolation, revocation, provider endpoint/response handling, authenticated-route rejection and fixture orchestration. Frontend/CRE type checks and lint pass. The browser smoke test completed a real streamed fixture run and checked provider selection/password masking, agent setup and account-pending integration views. Sponsor calls and live model calls remain untested at the user's request. Existing repository-wide Windows directory-fsync and build-memory blockers remain separate acceptance gates; passing these focused checks does not clear them.
